# 温蒂创作室：样张、失败恢复与耗时改进实施方案

状态：待实施。本文件是基于当前代码与真实作品日志的审查结果，不代表功能已完成。已补充实际界面的全流程效率审查，见第 13–16 节；新增项并入原有批次，不单独另起一次全面重构。

目标：用户能尽快看到并决定采用画面；失败时知道下一步；已收到的图片不因检查失败而重复生成；用更少调用完成同一篇作品。实现者可使用 Terra 或其他模型，按文末批次实施。

## 1. 审查结论与证据

当前 Git 基线为 `30a91e5`，审查时工作区干净。重点检查 `server/engine.mjs`、`bridge.mjs`、`server.mjs`、`workflow.mjs`、`compose.py`、`library.mjs`、`app/page.tsx` 与 `tests/workflow.test.mjs`。

真实案例为 `作品/7843159a-e825-47ee-81f3-a282c3c2dc05/`，当前标题《下班后的幸福时刻》，v2 方案共 6 页、13 格。审查时 `samplesApproved=true`，第一格处于待找回状态。

| 观察 | 当前证据 | 对体验的影响 |
| --- | --- | --- |
| 样张占据大量运行 | 37 个有事件日志的后台运行目录中，20 个为图片相关运行，其中 19 个是样张或样张局部修订 | 很久才能开始正式内容 |
| 图片相关运行慢 | 20 次运行约合 93 分钟，中位约 234 秒；其中第一格约 309 秒 | 每一次多余样张或重画都很昂贵 |
| 检查也有耗时，但不是全部 | 15 次画面检查合计约 9.2 分钟，中位约 26 秒；2 次方案运行合计约 16.5 分钟 | 优先减少多余生图，随后优化检查与方案输入 |
| 存在真实连接异常 | 27 条顶层 error 事件中，22 条含 `tls handshake eof` | 单靠改变按钮不能修好网络 |
| 明确无产出被识别为未知 | 第一格 response.txt 写明“生成工具返回网络连接错误，未产生任何图片，也未写入目标路径。” | 用户被要求反复找回不存在的原图 |
| token 展示需要解释 | project.json 记录输入 3,743,188，其中缓存输入 3,024,128，输出 48,948，累计记录 34 次运行 | 不能把输入总量等同于实际付费量或剩余可画张数 |

耗时是以各目录 prompt.txt 与 events.jsonl 文件修改时间差估算，包含工具执行、模型等待及重连，不能当作纯 image_gen 服务时间；运行目录包含历次修订，不是单次顺利完成一篇的基准。37 个目录与项目累计 34 次计数并不一致，现有统计不能视为完整账本。

关键原始证据：

- `.制作记录/1788692840032-69a69ced-第1页-第1格/response.txt`：明确网络失败且无图片。
- `.制作记录/1788685537360-01f9de48-样张-1-自动修订2/response.txt`：同类“未产出任何图片”表述。
- `.制作记录/1788661061006-f0192231-样张-2-自动修订1/response.txt`：运行自述已取得 2:3 图片，随后为追求 3:4 又重试两次。它说明历史流程存在内层多次调用风险，但不构成精确工具次数遥测。

不得声称已经证明代理是根因；也不得继续用“13 项测试通过”作为真实生图稳定的证明，现有测试主要使用伪 CLI 与本地夹具。

## 2. 产品决策与目标流程

**结论：做。** 主用户是需要完成漫画的创作者；核心问题是反复等候与不知如何继续。最小有用范围是样张决策、生成结果落盘、错误恢复和可验证的省时路径；补充范围仅包含减少重复输入、重复规划和强制模型调用的编辑与复用入口。先不扩展发布、多人账号、远程访问、全量素材管理或更换框架。

目标流程：

```text
输入需求 → 全篇方案 → 用户确认
                      ↓
       默认：生成首个正式分镜作为方向预览
                      ↓
       图片一到即显示，检查结果随后补充
                      ↓
       用户选择：采用 / 修改这一张 / 暂停
                      ↓
       复用已采用图片 → 绘制剩余分镜 → 排字与排版
                      ↓
       逐页查看问题 → 只处理受影响步骤 → 整篇验收 → 保存
```

新建作品提供两个明确选项：

- 默认“先看第一格”：第一格本来就是作品内容，通过方向确认后直接复用，不另付两张实验图成本。
- 可选“额外制作人物与场景样张”：用于新角色、新画风或复杂新环境；用户主动选择，界面说明额外图片数量。

这改变了当前工作指引中“首先生成两个样张”的通用默认，实施时同步修改工作指引和 README，保留用户确认完整方案这一门槛。既有作品不自动转换模式、不重画已经存在的样张。

## 3. P0：样张由用户确认，检查只给建议

### 3.1 当前问题

- `sampleProject()` 在原图完成后继续等待 QA，失败即串行自动修改，用户还没决定是否有必要就多次生图。
- `materialSampleIssues()` 仅排除比例问题，没有按 blocking/review/suggestion 决定是否必须处理。
- `approveSamples()` 强制两张图都 `qa.pass=true`，没有独立人工采用状态。
- 上次补丁在 `resume()` 检测任意一张达到两次上限后直接令 `samplesApproved=true`。它既不要求所有所需预览已完成，也不校验用户看到的图片版本；“继续”隐藏了“接受问题”的含义。
- `reviseImage()` 仍可再改，自动次数上限也没有覆盖人工修改、网络尝试和跨版本行为。它不是总预算。

### 3.2 实施

1. 把画面结果、自动检查和用户决定拆开：

```ts
type ImageDecision = {
  artifactId: string;
  contentHash: string;
  review: 'pending' | 'passed' | 'warnings' | 'failed';
  decision: 'undecided' | 'accepted' | 'revision_requested';
  acceptedAt?: string;
  acknowledgedIssueIds?: string[];
};
```

2. 每张可解码、来源可确认的图片保存后立即可见，检查中也能放大和人工采用。默认关闭样张质量自动重画；保留显式“只修一次”的操作。
3. 图片下显示“采用当前图片”“修改这一张”。方向预览全部已有用户决定后，显示“方向已确认，开始剩余画稿”。可以合成一次明确的“采用并继续”操作，禁止复用语义不明的 resume 来默默批准。
4. 已知问题可展开，用户采用时保存问题 ID 与图像 hash。人工采用不篡改 `qa.pass`，不删除旧检查结论。
5. 没文件、文件损坏、仍未知是否产出的任务不能伪装为可采用；确实需要跳过额外样张时，提供独立“使用固定参考继续”，只跳过可选预览，不能把缺失的正式格视为完成。
6. 用户采用后，迟到的 QA 不得反向取消其决定。对仍在运行的 QA 可发取消请求，但保留已收到结果，不承诺取消能追回已消耗额度。
7. 图像被修改后，采用决定只对旧 artifact/hash 有效，新图须重新决定。刷新或重启后决定仍存在。
8. 正式页采用相同机制：自动视觉建议可被明确人工接受；损坏文件、缺页、导出失败等客观问题仍阻止导出。

接口：新增 `POST /api/projects/:id/preview-decision`，请求带 `expectedRevision`、`planHash`、`artifactId`、`contentHash`、`decision`、`acknowledgedIssueIds`、`continueProduction`、`idempotencyKey`。服务端校验版本、任务冲突、文件可用性及适用预览集合；重复请求返回同一结果。

验收：第一张可用图无需等两次重画就能采用；所有正确图片不再因同一 QA 警告卡在循环；用户看旧版本后点击确认必须得到 409 并刷新，不得确认新版本图片。

## 4. P0：把生成、收图、检查分成独立步骤

### 4.1 真实失败路径

`generate()` 当前先等待整个 Codex 回合结束，再找文件，再做 QA，全部成功后才登记图片和清除 pending。网络异常、复制失败、校对失败都可能向用户呈现“生图没完成”。`recoverImage()` 又把查找与模型校对合在一起，点击“检查已有原图”可能发生新的模型调用。

`DEFINITE_NO_IMAGE` 漏掉“未产生任何图片”“未产出任何图片”等真实返回；`failure` 的异常文本也没有统一进入证据分类。用全文任意一句匹配作为最终结论同样危险：早期失败和稍后成功可能在同一个事件文件中。

### 4.2 新状态模型

```text
queued → preflight → running → output_located → persisted → succeeded
                       ↘ failed_no_output
                       ↘ result_unknown → recovering → persisted / needs_decision
persisted → review_queued → reviewing → passed / warnings / review_failed
```

每个状态属于独立任务。图片 persisted 后即发布 artifact，不依赖检查成功。QA 网络失败只能更新检查任务，不重置生成状态。

统一错误字段：`code`、`stage`、`message`、`evidenceLevel`、`hasArtifact`、`retryable`、`safeActions`、`taskId`。

| 错误 | 用户看到的结果 | 允许动作 |
| --- | --- | --- |
| 明确网络失败且无产出证据 | 本次未取得图片，已有进度保留 | 重试此图；不自动重画 |
| 回合断开，结果未知 | 正在检查这次任务的已有结果 | 本地检查、稍后检查；不默认重生 |
| 图片存在、复制失败 | 图片已找到，尚未存入作品 | 重试导入，不生图 |
| 图片已保存、QA 失败 | 图片已保存，自动检查未完成 | 人工采用、只重试检查 |
| 文字或版式问题 | 原图可用，当前页需排字/排版 | 编辑文案或布局，不重生图 |
| 登录、额度、能力缺失 | 具体依赖尚不可用 | 修复连接或等待额度；不伪装网络问题 |

### 4.3 收图与恢复细节

1. 任务启动前保存 taskId、attemptId、输入摘要、预期输出与关联 CLI threadId（收到事件后补记）。
2. 适配器按真实可获得的事件报告输出；若没有图片工具事件，明确 capability 为 unknown，不编造“已调用一次”。
3. 依次查找：任务登记的输出 → 适配器结构化路径 → 该 thread 的 generated_images 候选。response.txt 路径解析只作为兼容层，处理 Markdown、空格、非 /Users 主目录及 CODEX_HOME。
4. 不再无条件选线程里最新图片。候选多于一张时展示缩略图供选择；检查任务归属、mtime、内容 hash、真实路径与解码有效性。不得扫描其他任务私有目录碰碰运气。
5. 文件大小稳定且可解码后复制到临时文件，校验 hash，再原子改名；源图不删除。真实格式与扩展名一致，WebP/JPEG 不直接冒充 PNG。
6. “检查已有原图”变为纯本地操作，绝不启动 Codex；查找成功立即展示。“自动检查画面”单独列出是否会消耗模型额度。
7. 本地找不到不等于远端没产出；未知状态给出有限、明确的恢复入口。建议 5、15、30、60 秒本地检查后停止自动轮询，用户可之后再查。
8. 临时兼容分类覆盖实际无产出措辞，先查已保存文件与末次成功证据，再结合终态返回分类；只有旧日志证据时标记“运行报告无产出”，不得当成服务端可证明零请求。

## 5. P0：控制重试与网络失效，避免 token 空耗

`providerInvocations=1` 目前只是在启动 runCodex 前赋值；它不是内部 image_gen 实际调用次数。当前 events.jsonl 没有完整暴露图片工具次数，因此不能承诺已实现硬限制。

实施顺序：

1. 分别记录 `orchestratorRuns`、`transportReconnects`、`imageToolCallsObserved`、`imageToolCallsKnown`，观察不到的字段用 null。模型重连、一次工具重试、用户重画是三种不同成本。
2. 首先限制应用层：每个命令只入队一个生成任务，同图同输入并发重复请求合并；网络失败不自动创建新 image 任务。
3. 检查当前安装 CLI 的能力与事件协议，确定是否有受支持的单工具调用限制、工具启停及结构化产出。如果有再接入；没有时只做软约束和异常监测，在技术说明中写明限制，不编造参数，也不靠自然语言承诺“硬上限”。
4. 为 transport 断开增加有界预算：例如 60 秒内连续 3 次重连失败后停止本轮、进入本地结果核对。该阈值是待验证默认，不是网络成功率承诺。生成服务正在正常等待时不以“没日志”判死。
5. 连续多个任务发生同类网络错误后启动冷却，停止新生成并显示故障摘要。冷却后进行低成本连接检查；登录检查通过只代表登录可用，不代表图片服务可用。
6. 先使用只读配置与本应用日志区分 DNS、TLS、普通请求、模型流、图片生成/下载。不要再次直接关闭用户代理；此前断开代理也会断掉用户正在用的连接。
7. 如必须确认生图链路，单独安排用户授权的一张真实测试图，固定模型、输入和路线；普通聊天通不作为生图通的证明。不能默认切换付费 API 或浏览器后备渠道。
8. 超时按阶段定义：队列等待、连接、生成、输出导入、QA；停止时先保存状态，再核对已收到文件。总超时需参考实测分布，不能简单将 15 分钟缩为 1 分钟导致更多假失败。

## 6. P1：减少实际图片数和重复上下文

### 6.1 从首个正式格开始

新作品默认不产生额外两张样稿。已有正式格作为方向预览，通过后记录到同一个 panel slot，随后流程从下一格继续。当前例子有 13 格，正常路径从 15 张基础请求降至 13 张；更大的收益来自默认取消多次样张质量重画，而不是宣称每张图的服务速度会变快。

额外样张必须被正式分镜使用：生成时引用用户选定的样张 artifact，并以服装/地点/时间标签匹配，不要把泳馆披发样张机械带入办公室高丸子头场景。固定两张人设是身份基线，接受的预览只补充当前故事环境与造型。

### 6.2 提示词与计划一致

- 当前第一格外层提示词要求 `1034:725`，内部 q.prompt 却要求 `6:5`。建立唯一布局计划，进入生图前去除内部自由文本中的冲突尺寸、页内占比与多格指令。
- 图片任务只带本格动作、造型、环境、必要身份规则和相关参考；整篇连续性台账不逐格全文重复。
- 完整世界观仍在方案阶段读取与冻结，编译出带来源与 hash 的本篇规则摘要；不能为了省 token 删除用户明确的人物边界与固定参考。
- 按任务记录提示词版本、字符数、附件数及内容 hash；先测附件与上下文影响，再评估是否需要缩放预览参考。不得无检查压缩人脸参考。
- 方案可以用选定的编剧模型；生图编排和 QA 分别设置模型/思考力度。界面区分“编排模型”与“图片生成工具”，后者具体模型未知就如实显示。
- 以任务启动时的模型快照为准，用户切换只影响尚未启动的任务，不能从首页当前选择倒推历史模型。

### 6.3 让检查不阻塞出图

- 均衡模式：每张原图做本地校验；每页一次视觉检查；全篇一次连续性检查。精细模式才逐格检查。
- blocking 用于明确缺失、错误角色、明显严重画面错误；review 是需用户判断；suggestion 不触发重画。细微体积与审美评价不能自动滚入多轮生图。
- 用户已经采用某 artifact 后，对同一问题不能再自动阻断；新内容引入的新问题另行列出。
- 对已取得原图的分镜，恢复条件看 artifact 是否有效，不看 qa.pass。当前 generatePages 以 qa.pass 决定是否重画，会使“已有图、检查未过”的恢复路径再次消耗生图。
- 检查结果按 imageHash、规则版本、检查类型缓存。改文案只重排字与页级检查；改一格仅使对应页面和必要连续性复核失效。

### 6.4 排版失败不能默认变成重生图

- `compose.py` 当前以比例差超过 16% 直接建议重生图，比例在阈值内则中心裁切。提示词安全区不能证明中心裁切不会切掉手脚。
- 建立 image placement 数据：原图尺寸、目标框、cropRect、focusPoint、人工确认状态。超阈值先显示“调整布局/裁切”，让用户看预览；不拉伸、不模糊补边。
- 默认优先适配实际可用画幅，再调整格框与文字区；如果会改变已确认分镜结构，展示差异后确认。
- 提供页标题与文案编辑、排版预览、本地重排接口。reletter/recompose 必须落到可执行动作，不只是报错文案；重复重排同一数据不得再次调用模型。
- 内屏文字另列阶段：先让模型输出受约束的屏幕四角/遮罩数据，再用维护在仓库中的代码做透视排字。逐次让 agent 写新脚本是高成本且难复现的分支。无法定位时提供手动定位，不能偷偷把正文挪到屏幕外冒充成功。

## 7. P1：调度、额度与时间信息

### 7.1 先可靠串行，再有限重叠

P0 保持全局一个生成任务，先修重复请求和恢复。P1 在存储与锁完成后允许“一张正在生成、上一页正在检查/排版”，图片生成并发仍为 1。若当前提供方无法可靠隔离两个调用或网络错误上升，则恢复纯串行。

不直接 Promise.all 所有分镜。连续性、配额和 pending 单槽存储都不支持这种做法。

### 7.2 配额独立服务

- 当前每张生成前启动一个 app-server 读额度，最长等待 12 秒；bootstrap 也等账号读取，模型/用量缺一项可能拖到 8 秒。
- 将读取统一到 AccountService，去重 in-flight 请求，维护 `observedAt`、`lastAttemptAt`、`fresh/stale/unavailable`。失败时不把旧值的更新时间改成当前。
- 检查窗口时按 windowDurationMins 识别 5 小时/周；未知窗口如实展示。0%、null、缺失和非法字符串分别测试。
- 开始新付费步骤前读 30–60 秒内缓存；接近 10% 阈值强制更新，低于阈值保存并阻止新远程任务，已收到图片的导入与本地排版继续完成。
- 无法读到额度时显示“额度未知”，不假定充足或自动消耗一轮重试。新作品首次未知需要明确的继续选项；进行中的任务遵循用户已选策略。
- 不将 token 换算为可生成张数；输入、缓存输入、输出分列，失败任务也记录可观察用量。

### 7.3 有意义的进度

任务分别记录 queuedAt、startedAt、lastEventAt、outputLocatedAt、persistedAt、reviewCompletedAt、endedAt。用服务端时间做计时；暂停后停止本阶段计时，保留本篇累计活动时间。

网页显示“排队 / 正在生成 / 图片已保存 / 检查中 / 等你确认”，并展示已存图片。尚未可知的百分比不伪造；页数/图片数与计时分开。

耗时预估按同工具和阶段的最近成功样本给区间，样本不足就显示计时，不承诺几分钟完成。故障卡固定显示故障阶段、已保存内容、是否消耗新的生成机会以及唯一推荐动作。

接口动作返回 202 + taskId；按钮立即显示提交状态并禁用重复提交。读取请求设超时；写请求超时后先按 idempotencyKey 查命令状态，再决定是否重试，避免双发。轮询以 revision 去重并避免旧响应覆盖新状态，随后可使用 SSE 降低整项目轮询体积。

## 8. 项目结构与数据契约

当前 engine 同时管理文件、任务、审批、提示词、图像生成、检查、排版、导出。page.tsx 虽只有 68 行，但多数行含整片 JSX，不利于独立修改和测试。按职责渐进提取，保留旧导出作为适配层，不一次推翻工程。

```text
app/
  page.tsx                         # 页面装配
  features/creation/               # PreviewDecision、IssueList、Progress、作品编辑
  features/library/                # 现有作品与素材页面
  hooks/use-project.ts             # 请求、轮询、命令去重与版本控制
server/
  server.mjs                       # 服务启动与路由装配
  routes/projects.mjs              # 请求校验和命令入口
  domain/decisions.mjs             # 用户决定与审批规则
  domain/task-state.mjs            # 可验证状态转换
  services/production.mjs          # 流程调度
  services/recovery.mjs            # 输出查找、导入和任务对账
  services/quality.mjs             # 规则分级、检查与建议
  services/account.mjs             # 额度读取与缓存
  providers/codex-cli.mjs          # CLI 调用及实际事件适配
  providers/result-normalizer.mjs  # 旧日志兼容与错误分类
  storage/project-store.mjs        # 原子保存、版本比较和迁移
  storage/task-store.mjs           # 命令幂等、执行记录
  storage/artifact-store.mjs       # 图片 hash、来源和依赖
```

开始仍使用本地 JSON，不引入数据库服务器。每个项目一个写入队列，expectedRevision 做乐观校验，写入临时文件后 rename。若跨进程运行，增加单实例锁；锁包含 PID/启动标识，不能只凭文件存在认为进程仍活着。

任务记录至少包含：taskId、attemptId、commandId、projectId、planVersion、kind、targetSlot、inputHash、modelSnapshot、status、stage、timestamps、providerThreadId、artifactIds、error、usage、parentTaskId。运行记录不应简单截断为最近 80 项而丢失预算与历史依据；明细独立保存，项目只存摘要。

artifact 使用不变 UUID 和 contentHash；slot 如 panel:1:1 指向当前选中版本。禁止以“第1页-第1格”和“1-1-局部修订”混合作依赖身份。当前 artifacts.valid 仅写记录，复用时未统一检查，需让调度真正消费其有效性。

依赖：原图 → 内屏排字图 → 页面 → 全篇复核 → 导出包。新图替换时失效的是旧依赖分支，不得把刚生成的新图标成失效。样张审批引用具体版本，变更影响范围明确列出。

## 9. 旧作品迁移与这篇作品的恢复

1. 先备份 project.json 与任务索引，执行只读 dry-run 显示将迁移什么；不移动原图、不删制作记录、不改已经导出的成品。
2. schemaVersion 由 3 升为 4；迁移函数幂等，可重复启动而不重复造任务。
3. 旧 `qa.pass=true` 迁移为检查已通过，不凭此伪造用户确认；旧 samplesApproved 及 sampleAcceptance 保留来源标记。已经放行的作品不因迁移重新要求样张。
4. 这篇第一格先查任务目录、预期路径、关联线程候选，再读取明确无产出终态。证据一致后从未知恢复状态转为“本次未取得图片，可重试第一格”，禁止自动创建生图任务。
5. 不把当前已完成的两张样张重画；可以继续引用适用的样张。已采用历史记录与新人工决策分开标识。
6. 旧任务计数不可靠时记录“未知”，不要用文件名或错误句子出现次数推算实际图片调用总数。
7. 迁移完成后核对文件数、hash、可见页面与审批决定。回滚使用备份和旧 schema 兼容读取；回滚不能丢弃新产生图片，须另保留它们。

## 10. 实施批次与交付要求

| 批次 | 交付范围 | 进入下一批的条件 |
| --- | --- | --- |
| A：立即解除阻塞 | 独立人工采用接口、明确按钮、移除 resume 隐式批准、默认停止质量自动重画、真实失败措辞兼容 | 当前样张可人工放行；第一格失败不再要求无止境找回；重复点击不双发 |
| B：收图可靠 | 独立任务状态、先落盘再检查、纯本地恢复、图片登记、错误分类、命令幂等、schema 迁移 | QA 断网仍能看到图；服务重启不重复生成；旧作品不丢失 |
| C：减少调用 | 首格预览复用、样张引用、提示词去冲突、风险分级、检查缓存、文案/排版修订入口 | 正式首格不重复画；纯文字修改零生图；目标总图片数可核对 |
| D：耗时透明 | 配额独立缓存、任务时间轴、失败用量、后台检查与生成有限重叠 | 网络异常有阶段说明；额度保护经过边界测试；前端不空等账号读取 |
| E：真实验收 | 受控一张图试运行，必要时再做 2 页小作品；记录全部调用与耗时 | 有真实取图、人工采用、停止/恢复、导出证据；未验证部分明确列出 |

目录拆分在 A–D 随功能迁移进行，每批一个清楚的本地提交。不要先做一轮大重构才交付用户入口。不要为了验证启动用户现有制作队列；重启服务前必须确认无活动任务或等待明确暂停。

## 11. 必须补齐的验收矩阵

### 样张与审批

- 图已保存、QA 尚未完成：可以采用，稍后 QA 不覆盖决定。
- review/suggestion：不自动重画；blocking：显式说明，人工接受画面需记录，不能接受损坏文件。
- 一张有图、另一张缺失：不能假称两张完成；可选预览跳过走独立动作。
- planHash/contentHash 改变：旧确认被拒绝；重复确认幂等。
- 修改已采用图片：只让相关决定失效，已有其他图片仍可复用。

### 失败与恢复

- 使用第一格真实终态文字，以及“未产出任何图片”、工具失败但进程 exit 0 的夹具。
- 先失败后成功、有文件但终态包含错误、返回路径 Markdown/空格/自定义主目录。
- TLS 中断发生在生成前、生成后未收图、收图后未登记、QA 中，各自得到不同状态。
- 文件复制失败、截断图片、格式与扩展名不符、多个候选、越界/符号链接路径。
- 纯本地找回调用模型次数为 0；QA 失败恢复时 image 调用次数为 0。
- HTTP 写入响应丢失、快速双击、刷新、多标签页、服务重启、遗留子进程，不重复提交生成。

### 省时与布局

- 6 页 13 格的正常首格预览路径：总共 13 个应用层生成任务，方向确认不增加一张；额外样张模式单独计数。
- 输入提示词不存在互相冲突比例；真实画幅与模板不兼容时进入本地调整而非重画。
- 改一页文案只重排该页并按需检查，原始图 hash 不变，生成任务数不增加。
- 已收图未通过检查的 panel 在 resume 时不重画。
- 额外样张被实际引用；衣服/环境不适用时不误引用。

### 配额与性能

- 36%/58% 显示、低于 10%、等于 10%、0%、null、超时、过期缓存、未知窗口均测试。
- QA 用量、失败运行与缓存输入统计有来源；无 usage 时显示未知。
- 启动不等账号远程请求；提交动作建议本机 500ms 内确认接收（不包括远程任务完成）；图片落盘后建议 2 秒内可见。
- 时间指标区分等待、网络重连、生成、导入与 QA。改善目标：相同小作品减少额外图片与空重试；总耗时目标可设降低 30%，但必须以相同条件实测，不能作为上线承诺。

真实链路验证数量有限，成功一张不能证明稳定性达到某个百分比。先明确证据与样本量，再评价成功率。

## 12. 实施完成的定义

必须交付：逐条状态清单、对应代码入口、自动测试结果、真实验证范围、旧作品迁移结果、可回滚提交。标记只允许“完成且验证 / 已实现待真实验证 / 未实现”。

尤其不能将以下状态标为完成：只有错误提示没有处理入口；只有 artifacts 数组而调度不用；只有 providerInvocations=1 而看不到内层调用；只有后端接口没有用户按钮；只有模型夹具成功而声称网络修好。

最终用户应能回答三个问题：**这张图我是否可以直接采用？失败后会不会重复花一次生图？我现在等的是哪一步？** 三个答案必须在网页中清楚可见。

## 13. 全界面补充审查：把高频操作做成直接动作

本节依据实际 Chrome 创作室页面的状态、截图与代码交叉检查。查看了制作状态页、逐页方案、人物与世界、图片素材、我的作品；未提交生成、修改或素材分析请求。新建表单与编辑弹窗逻辑依据源码检查，未冒称所有窄屏布局和弹窗均已实测。

### 13.1 创作桌：画面优先，状态信息集中

现场制作页同时出现大标题、独立模型横栏、步骤条、两块重复故障说明、token 汇总、标签栏，下面才是画面区。当前还显示“已用时 0 秒”“unknown_result”以及“连接已就绪”，但作品实际上卡在失败恢复。这些信息缺少一致语义。

实施：

- 顶部固定一条紧凑工作栏：作品名、当前阶段、模型与思考力度摘要、额度、当前主操作。保留用户选择模型的入口，详细模型配置可展开。
- 中央是当前页或当前图；左侧页缩略图导航；右侧按需展开“问题与修改”。窄屏改为单列、底部主操作与可收起页导航。
- 故障合并为一张卡：第几页第几格、发生在哪一步、已保存什么、建议做什么。高级错误码和事件明细折叠，不能在正文直接显示 unknown_result。
- 无成稿时显示已确认方案的页格占位和已保存原图，避免只有巨大空白；以文字标注“等待生成”，不能使用假图模拟进度。
- 连接状态分成“账号已登录”和“最近一次生成连接异常”，不能用前者暗示后者正常。
- 当前主操作来自服务端 `availableActions`；前端不得靠散落的 status 条件自行推导审批与付费行为。

收益：减少找按钮与误解。此类布局调整本身不直接节省 token，只有避免误操作与重复任务才会间接节约。

### 13.2 每个动作说明范围与调用成本，但不增加层层确认

按钮使用“保存文案”“重排第 2 页”“修改第 2 页第 1 格”“只重试检查”，取代泛化的“按意见修改”“继续”。

调用模型的操作在按钮旁固定显示摘要，例如“将修改 1 张图，保留其他 12 格”；纯本地动作显示“本地处理，不调用模型”。无需每个动作弹出二次确认，已有明确提交按钮即可；删除仍保留用户要求的二次确认。

区分三类成本：本地处理、文字/视觉模型调用、图片生成。不得将“只检查”标成零 token，也不得编造“本次消耗 2%”之类精确订阅额度。

针对原图已落盘但 QA 未完成的情况，按钮明确为“采用此图”或“再检查一次”，让用户根据需要选择。

### 13.3 方案可以直接编辑；局部改动不能清空整篇成果

当前 `planProject()` 总是让模型返回完整计划，并重置 samples/panels/pages。逐页方案界面只有底部一个全局修改框，因此修改一句旁白也可能重新规划、重新确认和重画。

实施顺序：

1. 给页标题、旁白、对白提供直接编辑和本地草稿；保存不调用模型。
2. 给每页/每格提供“智能修改此处”，默认只传目标片段、必要邻接剧情、本篇规则摘要与问题，不附全篇历史。
3. 模型返回受限补丁而非完整文档：`targetId`、`baseHash`、允许修改字段、变更说明。服务端校验后再合并；未获授权的角色、页数、顺序与人物边界不能被越界修改。
4. 提交前由本地依赖分析展示影响：改旁白 → 该页排字；改画面动作 → 目标格待重画；改变跨页衣服/物件 → 列出真正受影响格。无法确定时列待复核项，不默认毁掉全部产出。
5. 全篇重构仍保留为明确的高级动作，提示影响范围并创建新版本；未变动的图像通过 hash/slot 引用继承，无需复制或重画。
6. 新版本需要用户确认变更后的方案，但可以继承未变部分的图像与决定。不能为了保留图片而绕开新版方案确认。

接口补充：`POST /api/projects/:id/plan-patch`，含 expectedRevision、basePlanHash、目标字段补丁、影响预览版本。影响分析必须由服务端重算，不能信任客户端“只改文案”的声明。画面中出现的屏幕文字、文字指令与剧情相关文案需要不同依赖处理。

验收：修改一处旁白不发起 planner 或 image 调用；同一页多处文字保存合并为一次排版；仅改第三页动作时，其他页图片 hash 与用户采用决定保持。

### 13.4 改图：选问题、圈位置、比较版本，再一次提交

- 问题列表按页格定位，可直接勾选要修的项并自动填入修改说明；不让用户手动重写 QA 的长段描述。
- 提供局部标注框与文字说明，保存归一化坐标和源图 hash。标注只帮助定位；不能宣传成提供方必定支持精确 mask 编辑。若无可靠 mask 能力，明确仍会整图编辑并需复查其他部位。
- 同一张图的多个待改点加入本地修改清单，一次提交同一张图；不同格仍保留独立任务和恢复边界，不为“批量”取消失败隔离。
- 新旧图并排/切换对比，支持“采用旧版”，纯本地切换，不调用模型。旧图列表显示生成时间、修改目的和已知问题。
- “修改”弹窗自动带入上次未提交草稿；提交后可离开页面，任务结果放在对应图上。避免“修改失败 → 内容丢失 → 重新描述”。

现有代码保留旧文件，但同版本的多次图片替换并没有完整可浏览的 artifact 历史。版本面板依赖第 8 节 artifact-store；旧图枚举只基于该任务记录、旁车文件与明确来源，不能把整个素材目录任意图片当作本格旧版。

### 13.5 本地草稿、工作位置与队列控制

当前只有新作品 brief 的部分字段存 localStorage，修改意见、编辑弹窗、文档草稿和当前作品/标签页主要在内存；全局 model/effort 又被新建、项目设置和素材分析复用。

- 草稿以 `projectId + planVersion + artifactId/docPath` 隔离，加入 baseHash；自动保存不调用模型。刷新恢复页码、标签页、缩放位置以及未提交意见。
- 切换作品清理或恢复对应草稿，禁止把上一作品的意见提交给下一作品；规则文件已变化时先显示冲突，不覆盖。
- 分离新建默认模型、当前项目模型和素材/文档分析模型；界面显示即将使用的配置，不随别处打开设置框被悄悄改变。
- 已生成/失败/未开始/待确认页格用可点击状态表示；允许“先做这一页”调整尚未执行任务优先级，不改变故事顺序或突破依赖。
- 提供“完成当前图片后暂停”，区别于“立即停止”。默认让已发出的生成完成并收图，随后不发新任务；必须即时止损时仍可停止，结果可能未知须说明。
- 长时间运行通知只在需要决定、失败、整篇完成时触发。页完成可显示非阻塞提示，免得每格弹窗打断用户；待处理事项持久保留，不依赖 4.5 秒消失的 toast。

这些主要节约人的时间和减少错误重提，不能单独计为模型 token 节约。

## 14. 素材、设定、作品复用：默认无需模型也能完成

### 14.1 真正的“手动添加素材”

当前 `/api/assets/upload` 上传后立即执行 analyzeAsset；`applyAssetProposal` 又要求模型 decision=keep。这不是独立手动流程：用户已知道如何分类也必须先花模型调用。查重还发生在分析之后，同图可反复分析。

改为三步可分离操作：

1. **上传/选取已有图**：本地校验、hash 查重、缩略图，返回候选；零模型调用。对完全重复图直接定位已有素材。
2. **手动分类保存**：用户填写分类、名称、标签、说明、用途（仅本篇/常用参考/正式基线），确认保存；无需模型批准。升级正式身份基线需明确确认与版本记录。
3. **可选智能建议**：用户有需要才点击。重复分析按 imageHash + 分类规则版本 + 用户分析要求 + 模型配置缓存；目录分类变化后缓存相应失效。

把 upload 与 analyze API 解耦；新增手动保存接口，同样做路径、类型、分类、体积和来源校验。模型判断 do_not_keep 只是一条建议，不能阻止用户有意保存；保留建议与人工决定来源。

默认将临时图放入“本篇素材”，不要为一次喜欢的动作污染长期身份基线。世界观与工作指引变更仍单独呈现差异并确认；素材 hash 重复也不应吞掉用户另行确认的文档变更，两个操作单独处理。

### 14.2 找得到、选得准，才能减少重复生成

- 图片素材增加本地搜索（名称/标签/说明）、分类、使用场景和最近使用筛选；不为普通搜索启动模型或向量服务。
- 单张素材可选“用于本篇”“用于这一格”，显示是否为身份基线、环境或动作参考；生成前的小型参考面板可删除错误附件。
- 按场景/服装保存用户确认的“参考组合”，避免每次重复描述；组合保存 ID/hash 与适用条件，不复制全部图片、不默认发送整个库。
- 选定旧画面可以直接作为格图复用，也可以只作为参考。这两个入口要分开，用户能看到裁切/分辨率是否适用。
- 复用故事模板只复制结构、可重复设定与用户选择的素材，不复制已批准状态或自动开始生图；新篇的小林权限必须重新明确选择，不能从模板隐式继承敏感角色授权。

先用本地精确 hash 查重，不做昂贵的“智能全库去重”。近似图可在用户整理时离线计算后提供候选，但不得自动合并或删除正式参考。

### 14.3 设定编辑只改需要改的章节

当前 suggestDocument 每次输入全文并要求返回完整修订文本，前端又只取 revisedText 覆盖编辑区；模型返回的 baseHash、说明和风险没有完整用于差异审阅。

- 文字设定提供章节导航、局部编辑、差异预览、恢复旧版；普通保存零模型调用。
- “智能完善”默认只针对选中章节与必要关联规则，输出受限变更；整篇改写为用户主动选择。
- 提案保留 baseHash、改动摘要及风险，保存前比较当前文件 hash；并发变更不允许覆盖。
- 固定设定与本篇例外分开存储；新增长期规则写明适用范围与来源，避免旧例外不断堆到每次提示词。
- 素材索引按元数据生成可读视图，避免模型每次分析再无限追加重复 Markdown。兼容现有人工条目，先导入并保留原文备份。

## 15. 把节省调用变成可执行的默认行为

### 15.1 出图前显示“这次要做多少工作”

页数不是图片调用数。方案确认处展示：正式格数、额外预览数、可复用格数、预计新生成任务数、检查模式。数字由 plan 与 artifacts 本地计算，不再额外问模型。

提供“减少镜头”建议入口：列出候选重复镜头及可合并内容，需用户确认才改稿。不得静默删剧情、降画质或把复杂画面简化成不能表达原意的镜头。未确定需求不自动启动第二个模型来“优化方案”。

可设本次授权的“最多新增图片任务数”和“最多质量修订次数”。任务入队前原子预留预算，重启后继续计算；未发出的任务取消可释放，已发出/结果未知任务保留计数。达到上限让用户明确追加，不自动重置。这个预算是应用层任务额度，不代表提供方实际 image_gen 次数或订阅金额。

### 15.2 模型只做需要模型的事

| 操作 | 默认执行方式 | 是否消耗模型 token |
| --- | --- | --- |
| 改标题、文案、页序、分类、标签 | 本地数据编辑与校验 | 否 |
| 排字、裁切预览、缩略图、打包 | 本地程序 | 否 |
| 查找原图、选择旧版、精确查重、搜索 | 本地索引与文件校验 | 否 |
| 构思剧情、局部改写、智能设定建议 | 用户触发文本模型 | 是 |
| 自动视觉检查、可选素材分析 | 用户策略允许的视觉模型 | 是 |
| 创建/修改位图 | 明确入队的生成任务 | 是，额度口径由提供方决定 |

即使页面显示“智能”，也不意味着每次刷新都应调用模型。预测耗时、统计、故障码解释、生成影响分析先用已记录数据和确定性规则。

模型路由默认以用户选择为准，不先开一个高思考模型判断该用哪个模型。可保存“省时/均衡/精细”配置，但必须展示对应检查环节、额外任务数与模型配置，不能只用形容词。

### 15.3 两级去重与用量归因

- 命令幂等解决“重复点击”；inputHash 缓存解决“不同点击但输入相同”。两者都需要，不能相互替代。
- 仅把相同内容、规则、检查目的、模型配置的成功检查作为缓存；未知结果不当作失败缓存后自动重生。用户明确“再试一版”才创建新的 attempt。
- 生图输出不自动当成任意新故事的缓存答案；只复用用户选定或同任务已确认的 artifact。
- 用量详情按方案、样张、正式图、检查、素材分析、文档建议分类；每条带 taskId、已观察用量、缓存输入、结束状态，未知用量单列。
- 默认页面显示“新增图片任务 / 重试 / 检查次数”，精确 token 放详情，不把累计百万输入数字当成唯一效率指标。评估以成功交付一篇所需的调用与修改次数为准。

### 15.4 页面性能优化：只计作交互收益

现在 bootstrap 把所有项目详情、文档全文、资产列表和旧作品清单混在一起；listAssets 每次计算全库 hash，图片媒体访问也调用该列表校验。作品和素材越多，打开越慢。

- bootstrap 返回轻量项目摘要，文档全文和图片版本详情按需读取。
- 维护文件 metadata/hash 索引，仅对变化文件重算；生成本地缩略图，列表懒加载，原图仅在放大时读取。
- 资源路由使用受控索引校验文件与真实路径；优化后仍禁止路径越界，不能为了省扫描直接开放任意路径。
- 计时器限制在进度组件，避免每秒重渲染整套作品；后台标签降低轮询频率，前台恢复时取最新状态。
- 弹窗需键盘焦点、Esc 关闭、输入标签与明确保存状态；未保存草稿可恢复。按钮间距和图片检视适配窄屏，避免误触重画。

这部分减少本机 CPU、磁盘与加载等待，不直接减少模型 token。不得把图片懒加载、轮询优化包装成模型费用下降。

## 16. 新增实施顺序与验收补充

新增项必须并入第 10 节各批次；E 的最终验收覆盖所有本轮纳入功能，不能先声称全部完成再留 UI 给下一轮。

| 编号 | 改动 | 并入批次 | 验收证据 |
| --- | --- | --- | --- |
| U1 | 主操作统一、成本/范围说明、去掉重复故障卡 | A | 用户能从页面明确判断下一步和是否调用模型 |
| U2 | 直接文案编辑与局部 plan-patch | C | 改一句话零规划/生图调用，其他图 hash 不变 |
| U3 | 问题勾选、同图合并修改、旧版比较与恢复 | B/C | 恢复旧图零远程调用，一次同图修改只入队一个任务 |
| U4 | 草稿隔离、位置恢复、完成当前图后暂停 | B/D | 刷新不丢修改意见，不跨作品串草稿，暂停不再发下一张 |
| U5 | 手动素材路径与分析前去重 | C | 手动上传分类零模型调用；同图分析缓存命中不再调用 |
| U6 | 搜索、参考选择和参考组合 | C | 找到旧素材并用于指定格；不发送无关全库附件 |
| U7 | 章节修订、差异审核与规则范围 | C | 修改单章不要求全篇模型重写；并发编辑不覆盖 |
| U8 | 图片任务预算与用量分类 | B/D | 重启、双击、未知结果均不突破授权任务上限 |
| U9 | 轻量加载与工作台布局、键盘/窄屏可用性 | D | 大作品列表不读取全部原图；主操作和问题位置可见 |
| U10 | 从旧作品复用格图/模板、生成工作量预览 | C | 复用不会自动生成、不继承审批，新增图数准确 |

避免同时塞入所有 UI：先交付 U1、U2、U3、U5，它们直接消除误操作、重规划、重画和强制分析；再按同一方案完成其余项。保持世界观、素材、作品三个现有主导航，不新增大量顶级栏目。

新增场景测试：

1. 在第 3 页修改一句话，刷新恢复草稿，保存后只重排第 3 页。
2. 同一图勾选两个问题，只发起一次修改；结果不满意时采用旧版，远程调用数不增加。
3. 手动上传已有图，立即提示已存在；选择“智能建议”才启动分析，重复提交使用缓存。
4. 一篇正在制作时打开素材整理，不改变该作品或新建默认模型配置。
5. “完成当前图后暂停”收到图后不发起下一次远程任务；页面显示暂停原因和已保存图。
6. 预算达到上限时不再生成；点“继续”不能绕过预算，需独立明确追加。
7. 修改规则章节后，旧项目仍按冻结版本执行；用户选择应用新规则时先显示受影响内容。
8. 相同作品流程在桌面与窄屏下都能找到采用、修改、暂停和下载；错误不仅出现在短暂 toast 中。

交付记录增加两列：**减少了哪类模型调用**、**只是改善本地操作还是已证明节省 token**。没有日志证据的节省比例不写成已达成结果。
