## 3. 判断与不确定性

**当前证据将阻塞定位在队列接收之后、网页生成执行之前。** 没有依据把本次问题归因于分镜 1 校对、画幅、代理、图片服务故障或账号额度不足。

已确认的程序缺口：

1. `server/chatgpt-web-provider.mjs` 的 `webWorkerStatus()` 只验证配置和历史会话文件存在，就返回 `ready=true`。历史记录不是当前接单能力。

仍需验证：

### A. 先验证接单机制（P1，首要）

1. 检查当前 Git 状态、作品快照、后台配置和最近队列记录，保护现有未提交修改。

3. 明确区分：请求已持久化、CLI 已接收、宿主已开始该回合、工作器已接单、网页已提交、图片已下载。
4. 给出有证据支持的故障点和最小可行修复。若本机服务没有受支持的自动唤醒方式，应明确说明需要的宿主操作，而不是伪造自动恢复能力。
5. 在证据不足时仍可完成本地状态和保护修复，但不得把整个真实接单故障标记解决。

### B. 接单确认与就绪状态（P1）

- 将“已配置/历史存在”和“当前已验证可用”分开；未经新鲜验证时显示未确认，旧 `verifiedAt` 不作当前健康证据。
- 复用既有 requestId 与持久化清单，让工作器真正开始处理时写入对应请求的接单证据和时间；不要用排队 CLI 返回值代写接单成功。
- 校验清单与当前请求、目标作品/方案身份一致，不能误用上一任务的状态。
- 分开接单等待与生成等待。接单超时应较早结束前台等待并准确提示；阈值需可测试、有依据，不机械把所有生成超时缩短。
- 若增加清单状态，同步 `readWebManifest()`、提示词协议、等待器、引擎、公开 API 和 UI；不可只改生产者或读取者的一端。
- 用户界面使用“等待后台接单”“已开始处理”“已提交生成”“原图已保存”等真实阶段，不展示无依据的进度。

### C. 超时、迟到与重复任务（P1）

- 接单超时、队列客户端退出或用户暂停，只能证明本机停止等待，不能证明排队任务已取消，也不能将 `submitted=false` 的旧快照当作最终无图证据。
- 保留所有请求与结果证据，继续允许找回既有原图。
- 禁止自动再次排队、重新提交网页提示词，禁止创建新后台来掩盖旧任务仍可能执行的问题。
- 若需要使旧请求失效，必须有工作器在实际提交前核验的有效性机制；单纯清空 pending、改 UI 状态或写“取消”并不能撤回宿主队列。
- 沿用已有单执行器与幂等机制；考虑网页后台生命周期可能长于本地等待器，不可在旧作业仍能发送时盲目放行另一条重复发送。
- 已提交任务的迟到下载仍须可找回，不覆盖别的图片、不跨版本挂接。
- 迁移旧清单时采取保守兼容策略，不删除历史记录，也不自动将旧 queued 状态转换为确定无产出。

## 修复执行记录（2026-09-10）

### A. 已证实原因与只读现场证据

- `codex-cli 0.153.4` 的本地帮助只说明 `codex queue` 是“向既有 session 排队消息”；它没有把 CLI 返回码定义为后台已开始处理。原实现把这两个边界合并成一次等待，因此 CLI 返回 0 但清单仍是 `queued` 时只能落到泛化超时。
- 原 `webWorkerStatus()` 以配置文件和历史 session 文件存在作为 `ready=true`。当前只读检查显示配置 `verifiedAt=2026-09-09T18:57:11+08:00`，历史 session 存在，但修复后返回 `ready=false, configured=true, historical=true`，提示当前接单状态尚未验证。
- 目标作品 `7843159a-e825-47ee-81f3-a282c3c2dc05` 当前仍是 `attention`，目标第 1 页第 2 格仍有 `pending`，当前任务为 `unknown_result`。只读扫描到 5 份网页清单：`queued=3`、`downloaded=1`、`failed=1`；3 份旧 `queued` 清单均为 `submitted=false` 且没有 `requestId`。这些旧证据未被改写、清空或转换成“无图”。

### B. 本地改动与修复前/后证据

1. **接单边界与当前就绪状态**：清单支持 `accepted`，请求创建时生成并持久化唯一 `requestId`；工作器真正开始处理时必须原子写入匹配的 `accepted/acceptedAt`，CLI 返回 0 不再代写。历史配置/session 只作为诊断字段，不再单独宣称当前 ready。
2. **身份与阶段等待**：`dispatchChatGptWebJob()` 分开队列客户端等待、接单等待和后续生成等待；只接受同一 `requestId` 的 `accepted/ready/submitted/downloaded`。接单超时返回 `WEB_WORKER_NOT_ACCEPTED`，保留清单，不自动重新排队。
3. **迟到与未知结果**：引擎把未接单保留为 `pending` 和 `not_accepted` 任务，不写“确认无图”，也不提供自动重试；原有队列退出、暂停、迟到下载和未知结果保护继续保留。
4. **实际操作出口**：HTTP 公开 `pending.webState/requestId/acceptedAt/submittedAt` 和任务 `webState`；UI 显示“等待后台接单 / 后台已接单，开始处理 / 已准备提交 / 已提交生成，等待原图 / 原图已保存”，未接单状态没有“继续制作”或确认无图重试出口。
5. **提示词协议**：后台提示词和队列消息均明确要求先写匹配的 `accepted` 接单凭据，再上传、提交一次和下载原图；未删除已有原图、历史方案、QA 或人工决定记录。

修复前先加入的 4 个负向边界回归均按正确行为失败：历史 session 被错误视为 ready；`accepted` 清单无法读取；CLI 0 但未接单返回泛化 `WEB_IMAGE_WAIT_TIMEOUT`；旧 request 的接单不能被区分。匹配接单路径作为正向证据保留；首轮模拟曾因 worker 启动预算过短而失败，调整为稳定的隔离启动预算后再验证，未放宽业务断言。随后补加“已接单但未提交”必须进入生成等待而非接单等待的阶段回归。修复后 `tests/web-worker.test.mjs` 共 **6/6 通过**，覆盖匹配接单后 `submitted`、`downloaded` 和隔离模拟原图落盘。
