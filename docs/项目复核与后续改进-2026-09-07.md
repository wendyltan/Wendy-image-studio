## 2026-09-09 Codex IAB 网页生图已跑通

本节取代下文 2026-09-08 对“普通 CLI 子进程无法取得 IAB”和“独立 Worker 尚未实现”的当前状态判断；下文保留为排障历史。

正式实现不再让临时的 `codex exec --ephemeral` 自己创建浏览器。项目建立一个专用 Codex 任务“温蒂创作室网页生图后台”，由该任务持有 Codex IAB；Web 服务通过 `codex queue --thread` 投递一次性作业，并轮询当前作业目录中的 `web-generation.json`。用户浏览器不会被打开，网页界面只可能出现在 Codex 客户端内。

每个真实作业保存 `worker-request.json`、完整 `prompt.txt`、`web-generation.json`、`events.jsonl`、`request.json` 和 `result.json`。清单状态为 `queued → ready → submitted → downloaded`，或 `failed`。只有清单写入 `submitted=true` 才计一次 provider 调用；提交前失败可安全重试，提交后缺少本地文件一律保留为结果未知。网页确认接口生成的防重复命令会写入结构化 authorization，后台在同一回合连续完成上传、唯一一次发送、等待和下载，避免回合结束清理 IAB 标签页。

真实验证项目为《下班后的幸福时刻》，项目 ID `7843159a-e825-47ee-81f3-a282c3c2dc05`，目标为第 1 页第 1 格。第一次验证在 `ready` 后因后台重复询问确认而结束，清单明确记录 `submitted=false`，未发生生图调用；据此修复了同回合执行与提交前失败分类。第二次验证只发送一次，ChatGPT 会话为 `https://chatgpt.com/c/6aa14053-1c84-83eb-9e66-cc9c9fa3d628`，原始 PNG 已下载并挂接到项目：`v2/素材/第1页-第1格-1788952606003.png`。

最终文件为 1497×1051 RGB PNG，大小 1,800,675 bytes，SHA-256 为 `03b609083b5a61cade05be2679021e5a9db16b9a678667caa4a970702f69d32d`。项目状态为 `paused`，`pending=null`，当前图片任务为 `artifact_saved`，`providerInvocations=1`；按单图重试边界没有继续生成其他分镜。完整测试 40/40 通过，生产构建通过。

## 2026-09-08 图片生成渠道切换（历史排障，已由上节取代）

已把新图片任务从内置图片工具切换为 `chatgpt-web-iab`：后台 Codex 必须在隐藏的 Codex 内嵌浏览器中打开 `chatgpt.com`，逐项上传参考图，通过聊天界面只提交一次请求，下载网页原图并写入既有素材目录。温蒂创作室页面、方案确认、样张确认、单格流程、QA、排版、恢复和验收行为保持不变。

执行边界同时在两层固定：任务提示词禁止图片接口和外部浏览器；CLI 关闭 `image_generation` 与 `browser_use_external`，浏览器后端环境只允许 `iab`。新任务不再从 `$CODEX_HOME/generated_images` 认领图片；该目录仅用于没有 provider 标记的旧任务找回。每次运行写入 provider、参考文件摘要、目标路径、网页执行记录和结果证据。

代码与夹具流程已经验证；测试覆盖 IAB 专用提示词、CLI 禁用图片工具和外部浏览器、IAB 不可用时的确定未提交、精确落盘和旧任务兼容。真实能力探测没有发送消息或上传文件，结果为普通 CLI 子进程无法创建 IAB：`Browser is not available: iab`。这是 Codex 宿主按会话 ID 绑定内嵌浏览器造成的运行时能力缺口。生产环境默认在子进程启动前失败，只有验证宿主已提供后台 IAB 并设置 `WENDI_CHATGPT_WEB_IAB_READY=1` 后才放行，因此不会为已知不可用能力继续消耗额度。当前实现不会打开用户 Chrome，也不会偷偷回到图片接口；真实网页生图尚不能标记为通过。

## 2026-09-08 网页与真实生图验收

- 用 Computer Use 在真实网页打开“修改名称”和“更换模型”弹窗。主要输入自动获得焦点，Esc 可关闭，关闭后焦点返回触发按钮；原生 `dialog` 已在实际页面生效。
- 发现并修复恢复流程死路：`pending` 存在时 `imageRetryState` 原先隐藏 `unknown_result`，导致页面只有“检查已保存图片”，没有用户明确承担重复风险后的单张重试入口。现在旧 pending 仍可继续本地查找；对应任务已经是 `unknown_result` 时，同时显示明确重试入口。
- 用户明确重试未知结果时，旧 pending 会写入 `supersededPending`，带 `supersededAt` 和 `reason=explicit_unknown_result_retry`，然后只为目标图片创建一次新任务。旧文件路径、运行目录、提示词和任务 ID 都保留供追溯。
- 发现并修复第二个死路：前端幂等键原先只使用项目 revision。生图失败不一定改变 revision，因此新一次明确重试可能被识别为旧命令重放。现在幂等键使用当前图片任务 ID；同一任务的重复提交仍去重，新失败任务可以获得新的单次重试命令。
- 第一次网页请求确实启动了单图任务，但在构建后重启服务时被中断。应用保留了新 pending 和任务记录，没有把它当成确定无图，也没有继续生成其他分镜。
- 最终实测任务 ID：`509df071-b647-4b28-aaef-4c93276ab586`；运行目录：`.制作记录/1788854682620-4ba95ed5-第1页-第1格`。网页全程显示只重新生成第 1 页第 1 格，`providerInvocations=1`。
- 最终任务运行约 5 分 37 秒后结束。子任务已读取两张温蒂人设并进入一次内置 imagegen 调用；直接错误为 `network error`，目标为 `https://chatgpt.com/backend-api/codex/images/edits`。`result.json` 记录 `outcome=artifact_still_unknown`、`connectionRelated=true`、`reportedImageCount=0`、`candidateCount=0`。
- 结束后再次从网页执行本地查图，没有找到可挂接图片。系统停在 `unknown_result`，未自动发起第二次生图；本篇调用计数从 39 增为 40。

结论：项目内的恢复、幂等、单图边界和事实来源逻辑已按预期工作；这次没有生成成功的直接原因仍是到图片端点的网络发送失败。独立 Worker 可以避免 Web 服务重启中断任务，但不能修复本次远端图片端点网络故障。

### P1：跨进程恢复所有权

位置：server/job-store.mjs recoverable、cancel；server/engine.mjs recover。
