## 发现的问题（按优先级）

### F1 · P1：恢复队列会移除仍在运行的执行者锁

位置：`server/job-store.mjs:24-30`。

`heartbeat()` 只更新任务 JSON 的 `heartbeatAt`，而 `recoverable()` 判断的是锁目录的 `mtime`。运行超过两分钟后，即使心跳刚更新，另一进程启动恢复时仍会将任务标为 `interrupted` 并删除全局锁。代码也没有核实执行进程是否存活。

独立临时目录复现：领取任务 A，将锁目录时间模拟为三分钟前，更新 A 心跳，然后调用恢复。结果为：

```text
fresh heartbeat: 2026-09-07T07:07:57.382Z
recover result: interrupted, owner=live-owner
second owner can claim: true
old owner removed new lock: true
```

最后一项来自 `finish()`：旧 owner 结束任务 A 时仅核对 A 的 owner，没有核对当前全局锁属于谁，因而还会删除任务 B 的新锁。

影响：服务重叠启动或恢复时可能出现多个执行者，破坏全局单任务约束，带来并发生图风险。

建议：使用带任务 ID、执行者身份及有效代次的锁，恢复前核实进程存活；结束时只能释放自己当前持有的锁。心跳超时本身不能授权接管。

验收补充：活跃长任务不能被回收；旧 owner 不能释放新 owner 锁；两个进程不能同时领取。

### F2 · P1：领取锁失败后永久保留 active，任务无法继续

位置：`server/engine.mjs:67-79`，重点为第 72 行。

任务进入 `active` 后，若 `claim()` 返回空，直接 `return`，不会进入后面的 `finally` 清理，也没有定时再次领取逻辑。

独立临时目录复现：预先持有全局锁，再调用 `job()`。结果：

```json
{"invoked":false,"active":true,"queue":{"status":"queued"},"status":"draft"}
```

影响：没有实际执行，却一直显示忙碌；再次操作被“这篇正在制作”拒绝。尤其是异常退出后两分钟内重启，旧锁尚未被回收时容易触发。两分钟后也不会自行恢复，因为恢复扫描只在启动时调用。

建议：领取失败必须有明确的可取消等待/再次调度机制；所有退出路径清理或正确保留可调度状态，不得只保留不可执行的内存锁。

### F3 · P1：仍把网络错误后的模型说明当成“确定无图”

位置：`server/engine.mjs:158-162`、`:305`、`:320-324`；`server/bridge.mjs:49-61`。

提示词仍要求“若工具返回网络或连接错误，立即结束并明确说明没有产出”。分类器随后用自然语言正则将这种说明判为确定无图。

隔离调用分类器，输入“生成工具返回网络连接错误，未产生任何图片，也未写入目标路径。”，得到：

```json
{"outcome":"no_image","reason":"reported_no_image_after_connection_error","connectionRelated":true}
```

影响：远端可能完成而本地未下载的情况被错误放行到重试；直接违背原方案要求。历史恢复同样使用此判断。

建议：删除强制无产出说明，区分结构化提交/拒绝证据与模型文案；仅有网络错误时保留 `unknown_result`。现有测试“explicit no-image evidence never falls into the uncertain recovery path”实际锁定了这个错误假设，需要修改测试预期。

### F4 · P1：原始“前端能重试、后端拒绝”问题没有修复

位置：`app/page.tsx:79`、`:94`；`server/server.mjs:109-118`、`:187-197`。

前端根据 `currentTask.status==='failed_no_output'` 显示重试按钮；后端仍只认可 `pending` 或 `lastFailure.definiteNoOutput`，目标提取也不读取 `currentTask.target`。

触发条件：`currentTask=failed_no_output`，但 `pending=null`、`lastFailure=null`。这正是前次诊断发现的状态。`recover()` 也没有把该组合统一归一化。

结果：点击按钮仍返回“请先确认没有生成图片”。当前 HTTP 重试测试设置了 `lastFailure`，没有覆盖真正出错的组合。

建议：使用统一的任务恢复资格判断；兼容旧状态时先核对证据，不能为消除按钮错误而扩大“确定无图”的范围。

### F5 · P1：“只重试这一张”仍会推进后续分镜

位置：`server/server.mjs:197`；`server/engine.mjs:421-452`、`:480-487`。

重试接口记下目标后清空失败状态，调用通用 `resume(p)`，没有把目标作为执行边界。正式制作会进入 `generatePages()`，其循环在当前图片成功后继续生成后续缺失分镜。

影响：用户只确认重试一张，系统可能继续消耗额度生成整篇；明确违背方案的单图重试范围。测试方案只有一页一格，无法暴露此问题。

建议：单独执行指定目标，保存和必要校对后暂停；通用“继续制作”维持整篇推进。新增至少两格的测试，断言第二格未调用生图。

### F6 · P2：暂停会在产物核对之前抛出，未满足统一收尾

位置：`server/engine.mjs:306-317`；`server/server.mjs:246-256`。

CLI 返回后先调用 `checkpoint(signal)`。若用户暂停或服务关闭触发 abort，将直接跳过文件核对、`result.json` 和原图登记。当前关闭流程仍会 abort 所有任务。

影响：已经落盘的图片无法在本轮自动登记，需要之后手动找回。不是已证实的数据丢失，但不符合“暂停也先核对产物”的承诺。

建议：将本地结果核对放入不受新远端调用取消影响的收尾路径；暂停只阻止后续生图和校对，给本地保存留出有界完成时间。

### F7 · P2：候选路径未严格证明归属，可能认领输入参考图

位置：`server/bridge.mjs:49-55`；`server/engine.mjs:312-317`、`:491-496`。

`imagePaths` 从回复和事件中的文本/路径字段提取；消费方只检查路径存在，未要求属于当前输出目录或当前生成线程，未排除输入参考图和编辑原图。只有一个已存在路径时就会复制并认领。

触发示例：失败回复包含一个输入参考图绝对路径，而没有有效生成结果。该文件可解码且唯一，仍可能通过候选检查。线程内多候选测试不覆盖此路径。

建议：路径解析只作为线索；结合输出事件、当前任务清单、输入排除集合和目录归属判断。新增“只有参考图路径时不能判成功”的测试。
